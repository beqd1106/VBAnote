## q-sec-006
問題: IAMで権限を設計するときの「最小権限の原則」とは、どのような考え方ですか。
1. 管理者権限をすべてのユーザーに配る
2. いかなる権限もまったく一切与えないこと
3. 全員にすべての操作権限を与える
4. ◎業務に必要な最小限の権限だけを与える
解説: 最小権限の原則は、各ユーザーやサービスに『仕事に必要な分だけ』権限を与える考え方です。万一漏洩しても被害を最小化でき、セキュリティの基本となります。
×1: 管理者権限の乱発は危険です。
×2: まったく与えないと業務ができません。
×3: 全権限付与はリスクが大きく、原則に反します。
指摘(種類5): 不正解の1と3がともに全権限の付与 ／ 直し案: 3を「業務に必要な権限を定期的に見直さない」に差し替え、×3も見直し不足の説明にする。

## q-sec-018
問題: 通信中のデータを盗み見から守るための基本的な対策として、最も適切なものはどれですか。
1. 入力したパスワードを画面にそのまま表示する
2. 通信の暗号化の設定を無効にしたままにする
3. 通信の内容を暗号化せず平文のまま送信する
4. ◎HTTPS（TLS/SSL）で通信を暗号化する
解説: 通信中（in transit）のデータはTLS/SSL（HTTPS）で暗号化して守ります。保存データ（at rest）はKMSなどで暗号化します。両方の保護が重要です。
×1: パスワード表示は危険です。
×2: 暗号化の無効化は危険です。
×3: 平文は盗聴の危険があります。
指摘(種類5): 不正解の2と3がともに通信を暗号化しない ／ 直し案: 2を「通信相手の証明書を検証しない」に差し替え、×2も証明書検証の説明にする。

## qd-sec02-e9
問題: 10人の開発者に同じ権限を効率よく与えたいとき、最適な方法はどれですか。
1. 1人ずつ手作業で同じ権限を個別に設定する
2. 全員でルートの認証情報を共有して使う
3. 全員に個別のアクセスキーを配って使う
4. ◎グループにポリシーを付け全員を所属させる

×1: 1人ずつの手作業は非効率で漏れも生じます。
×2: ルート共有は非常に危険です。
×3: 共通キー配布は漏えいリスクが高いです。
指摘(種類4): ×3は「共通キー」だが選択肢3は「個別キー」 ／ 直し案: ×3を「個別キーの配布だけでは権限を一括管理できません」に変更する

## qd-bil05-e5
問題: 部署ごとに分かれた複数アカウントの請求を1本化し、割引も効かせたいときに最適なのはどれですか。
1. アカウントを無理やり1つに統合してしまう（部署分離が失われる）
2. ◎AWS Organizationsで一括請求する
3. 各アカウントで別々に支払いを続けていく（合算の割引が効かない）
4. 請求をまったく統合せずそのまま放置する（管理も割引も進まない）
解説: 正解はAWS Organizationsの一括請求（Consolidated Billing）が、複数アカウントを別々のまま保ちつつ請求だけを1本化できる仕組みだからです。使用量を合算することでボリューム割引の基準にも達しやすくなります。アカウント自体を無理に1つへ統合したり、各部署が別々に支払いを続けたりする方法とは異なり、部署の独立性を保ったまま管理と割引を両立します。
×1: 部署分離を保ったまま1本化できるのが一括請求の利点です。
×3: 別々の支払いでは合算の割引が効きにくくなります。
×4: 放置では管理も割引も進みません。
指摘(種類5): 選択肢3と4はいずれも請求を統合しない ／ 直し案: 4を「コスト配分タグだけで一括請求する」に差し替え、×4も修正する

## b-tec-12-15

1. リアルタイム処理
2. ◎バッチ処理
3. ストリーム処理
4. 暗号化処理

×1: リアルタイム処理は、発生したデータをその場で処理する方式です。
×3: ストリーム処理は、流れ続けるデータを逐次処理する方式です。
×4: 暗号化処理は、データを読めない形に変換する処理です。
指摘(種類5): 不正解の1と3が解説で同じ方式とされる ／ 直し案: 3を「手動処理」に変更し、×3を手作業による処理の説明に差し替える
